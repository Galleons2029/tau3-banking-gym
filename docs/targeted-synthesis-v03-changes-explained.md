# 从 Worldgen-V2 到原生银行定向合成：这次改了什么，为什么这样改

> 更新：2026-09-19。面向希望理解数据策略、而不必阅读实现代码的读者。
>
> 本文以用户确认用于 v03 训练的 **13,395 行 targeted 数据**为旧版比较对象，以 **native v03 r10 及 repair1–repair6** 为新版。更早的 8,630 行导出不是同一批数据，不能混在一起归因。
>
> 核心变化是：从“在虚构业务中练习通用能力”，转为“使用银行测评的公开政策、工具协议和业务后端，生成新的客户与业务实例，练习真实的银行决策”。这说明训练内容更有针对性，**不代表已经证明重新 SFT 后官方成绩提高**。

## 1. 先说明几个容易混淆的概念

| 名词 | 通俗解释 |
|---|---|
| 世界/环境 | 银行有哪些政策、工具、账户和业务规则，相当于题目所处的工作场所 |
| task/任务 | 一位客户在某个初始状态下提出的业务需求，例如处理两张卡上的争议交易 |
| 教师轨迹 | 教师模型完整处理一次任务的过程，包括查文档、询问、调用工具和最后回复 |
| SFT 样本 | 经过成功判定、质量审核和格式检查后，可以交给学生模型学习的轨迹 |
| 准入 | 先判断题目本身是否正确、信息是否足够、是否存在合法解法 |
| 反例 | 故意漏办一张卡、用错金额或错误批准，验证检查器能否发现这种错误 |
| 冻结 | 在采样前固定任务配额、种子、配置和代码版本，不能看到结果不好就悄悄换题 |

一题固定采样四次，可能产出 0～4 条合格样本。因此，“四百道题”“一千条轨迹”和“一千行训练文件”不是同一个量；把同一条数据重复五遍，也不会增加五个业务实例。

## 2. 失败报告到底指出了什么

[v03 分析报告](../data/calibrations/docs/v03.md)指出两项反复出现的问题：

1. **不会稳定地使用可发现工具协议。** 没有先解锁就调用，外层参数名错误，或者把业务参数放错位置。
2. **编造工具名。** 使用环境里不存在的名字，或者把真实工具的数字后缀记错。

还有取错账户、参数枚举错误、漏必填字段，以及业务判断方向错误。例如 task_051 应当因高利用率拒绝提额，模型却执行批准。即使前面的核身和检索都正确，关键写操作错误仍然会导致失败。

报告中的统计需要准确理解：

- A/B 是**工具错误事件的分类占比**，不是“多少比例的失败任务只由这两个原因造成”。按报告表格相加，三轮 A+B 分别为 **60.7%、69.0%、55.5%**；不能照搬正文中“稳定 60–68%”作为精确结论。
- 报告各轮涉及不同训练版本，不能直接用跨轮分数证明某项数据改动导致涨分或掉分。
- 报告认为协议和业务能力是主要问题，不支持把主要工作继续放在网关转译或简单增加步数上。

所以，这次数据改进同时处理两件事：**工具能正确执行，以及执行的业务决定本身正确。**

## 3. 旧版究竟如何合成

### 3.1 旧版已经有业务生成和验证，并非只改写一句话

旧 targeted pipeline 根据 F1–F8 等失败标签选择配方，先生成虚构世界中的账户、卡和案件，再确定政策、业务目标与参考动作，最后生成任务表达并采集教师轨迹。

其流程可概括为：

```text
失败报告 → 能力配方 → 虚构世界与案件状态
         → 受限契约、政策和文档 → 正反例与盲解检查
         → 教师执行 → 成功筛选 → 协议转换、错误轮屏蔽 → SFT
```

它已经包括对象枚举、分页查询、日期边界、金额计算、用户交接、相似签名干扰、额外写入检查等机制。这些工作保留了价值。

但是，其主要业务终态集中在：案件是否处理、调整额或责任额是多少、转到哪里、如何交付。账户和卡更多是查找案件的连接关系，**没有真正实现银行提额批准/拒绝、支付、销户等业务状态变化**。

例如，旧题可以训练“找齐三个对象并逐一更新”，却未必训练到“查询支付历史和待处理申请后，决定拒绝这张卡的提额，同时批准另一张卡”。两者都有多对象和长流程，但业务推导不是同一件事。

### 3.2 旧文档较容易检索，表达也偏程序说明

对用户确认的旧批次做全量审计，得到以下结果：

| 审计项 | 旧批次实际情况 | 含义 |
|---|---|---|
| 业务实例 | 2,679 个 | 与训练行数不同 |
| 完整教师轨迹 | 8,179 条不同轨迹 | 平衡采样和 focus 曝光后形成 13,395 行 |
| 每个世界可访问文档 | 9～12 篇，中位数 11 | 总计 27,615 篇不等于单个教师面对这么大的文档库 |
| 正解相关文档占单世界文档库 | 约 55.6%～66.7% | 找到相关材料的搜索空间较小 |
| 安装的官方文档库 | 698 篇，平均每题约 9.89 篇相关文档 | 相关文档约占整个库的 1.42% |
| 文档渲染 | 全部为 controlled text | 有自然语言重写能力，不代表这批实际启用了它 |
| 文档中的实现表达标记 | 10,998/27,615 篇 | 相当多的规则直接带程序式谓词或实现痕迹 |
| 跨品类依赖 | 没有 | 很多长流程仍是重复案件处理 |

旧文档往往把操作契约集中放在一篇材料中，并将执行条件直接转成文字。它有利于保证生成的规则与执行器一致，但与银行真实的多篇政策、例外规则和业务证据分布仍有距离。

这里的问题不是“文档一定要更长”，也不是“随机工具名一定不好”，而是模型是否练到了**从分散的真实业务证据推导动作**。

### 3.3 不能把已经修复的旧缺陷再次归给这批数据

这一点对理解改进方向很重要：

- 早期 V2 外层字段叫 `capability`，原生银行叫 `agent_tool_name`。但用户确认用于 v03 的批次已经转换过；不能说这批仍在正向教授错误字段名。
- 全量审计发现 **41,024 次 unlock 使用了正确的 `agent_tool_name`**。
- 已识别出的未先成功 unlock、未知别名、无公开来源的选择器及错误调用轮，都已屏蔽训练标签。
- 该批不存在目录浏览和一次读取全部客户记录的快捷工具。
- 旧批次未保留非空 `reasoning_content`，不能根据教师开启 thinking 就推断学生学习了这些推理文本。

因此，旧数据仍未解决 v03 问题，不能简单解释成“根本没教 unlock”或“所有错误都作为答案训练了”。更有证据支持的结论是：**格式清理做了，但银行业务、工具边界、检索环境和训练曝光仍有覆盖缺口。** 具体因果贡献还需要对照实验。

完整审计见：[旧批次文档与数据审计](../data/calibrations/docs/worldgen-doc-audit-20260919.md)。

## 4. 新版如何合成：在银行环境里生成新业务

### 4.1 保留框架，改变业务环境

现在使用原生 `banking_knowledge` 的公开政策、数据结构、工具签名与 `bm25_grep` 检索，生成新的客户、账户、余额、历史、交易和请求。

这不只是给 V2 的工具换一个字段名，也不是把官方 97 题换个客户姓名。覆盖规划会参考官方任务出现的操作，但不把官方客户初始状态或标准答案复制为新题。

```text
v03 与前序失败报告
    ↓ 抽取有来源的结论，隔离评分疑点
冻结业务配额、操作覆盖、难度、四个 seed
    ↓
生成新客户事实、业务依赖和正确目标
    ↓
确定性编译 + 独立业务检查 + 正反例
    ↓
GLM / Gemini 分别在公开环境中盲解与审核
    ↓
有效任务：GLM 固定四次教师采样
    ↓
环境成功判定 + Gemini 质量/信息边界审核
    ↓
干净成功轨迹 → 主训练集
成功但中途犯错 → 单独恢复集
四次都无合格样本 → 难题池
不完整证据 → 保留缺口，不伪装完成
```

模型并不自由决定业务规则。GLM 可以分析报告、提出生成策略和表达，但金额、日期、枚举、状态变化仍必须落入已实现且可检查的生成器。

### 4.2 新旧差异一览

| 方面 | 旧 targeted V2 | 当前 native r10 |
|---|---|---|
| 主要目标 | 在虚构世界练习可迁移能力 | 直接练习银行业务和协议 |
| 新实例 | 新案件、状态、对象关系 | 新账户、交易、历史、资格、资金依赖和业务请求 |
| 核心操作 | 案件处理、金额估计、路由、交付 | 提额、拒绝、争议、补卡、关户、转账、限制调整等 |
| 文档 | 每世界少量生成文档 | 原生公开银行政策库 |
| 工具边界 | 较窄的常驻工具面与合成操作 | 原生普通工具、隐藏 agent 工具、用户工具的实际边界 |
| 协议学习 | 原 V2 协议，导出时修正接口 | 在原生 unlock → call 环境实际执行并验证 |
| 判定依据 | 契约、终态、义务和反例 | 继续保留，并补充独立金融判断、时序、真实工具结果 |
| 覆盖统计 | 能力标签、配方、实例数 | 业务族 + 具体操作 + 分支 + 难度 + 反转对 |
| 主集筛选 | 成功轨迹中可保留已屏蔽的错误历史 | 主集要求整个轨迹无工具/协议错误；恢复另存 |
| 推理文本 | 此次审计的旧批次未保留 | 原始 reasoning 严格审核后保留，不补写 |
| 扩量判断 | 生成、成功和导出检查 | 先小规模交付，再要求外部训练及配对评测回执 |

### 4.3 当前配额强调真实决策分支

| 主业务族 | 前 400 题 | 全量 3,000 题 | 要练习的行为 |
|---|---:|---:|---|
| 提额 | 100 | 750 | 批准、拒绝、提交前停止、多卡分别决策 |
| 交易争议 | 80 | 600 | 识别交易、信用卡/借记卡不同条件、责任与补偿 |
| 补卡与关闭 | 60 | 450 | 区分换卡和销户，处理前置条件与等待期 |
| 账户和资金 | 48 | 360 | 开户、信息更新、资金流转及相应资格 |
| 借记卡安全 | 40 | 300 | 激活、冻结/解冻、解除限制、临时限额 |
| 优化与计算 | 32 | 240 | 产品选择、收益、推荐和利息纠正 |
| 用户交接 | 20 | 150 | 让用户实际完成其负责的操作 |
| 升级与边界 | 20 | 150 | 判断是否转人工，以及使用正确原因 |
| **合计** | **400** | **3,000** | |

全量 750 道提额题中，250 道批准、300 道拒绝、100 道提交前停止、100 道多卡混合。拒绝覆盖七种有政策依据的原因。超额申请应在提交前停止，不能为了凑某个枚举而制造不合规流程。

此外，在业务族内部为少见操作保留配额。这样不会出现“争议题很多，但某种实际操作一次没出现”的假覆盖。覆盖按任务计数，重复调用同一个工具不会把覆盖数刷高。

70% 当前缺口、20% 能力保持/回放、10% 组合探索的来源结构保留。原生路线不把旧虚构案件轨迹直接当成银行回放数据。

### 4.4 长任务来自业务依赖，不靠无意义步骤凑长度

参考动作数仍按 `1–4 / 5–9 / 10–14 / 15–19 / 20–29` 分桶，占比为 `15% / 25% / 25% / 20% / 15%`，同时记录实际业务操作数。

延长任务应通过更多目标账户、不同决策、资金依赖或用户交接实现。例如先完成必要的资金处理，再办理后续业务。反复解锁、重复读同一条记录不能当成业务难度增加。

一个实际修正是：删除补卡参考流程中政策并不要求的销户专用查询；若需要长任务，就增加真实需要办理的卡，而不是保留无意义查询。

## 5. 如何逐项针对 v03 的失败

| 报告问题 | 新版的训练措施 | 如何检查 |
|---|---|---|
| A：未解锁就调用 | 教师在真实原生工具环境执行两步调用 | 漏 unlock、错误时序、同批解锁并调用等协议反例；审计真实返回 |
| A/D：外层和内层参数混淆 | 外层选择工具，内层 `arguments` 保持 JSON 字符串 | 错 selector、对象代替字符串、参数挪到外层均检查 |
| B：幻觉工具名 | 从公开文档发现完整名称，读取 unlock 返回的真实签名 | 错后缀、不存在工具、隐藏工具直接调用的反例 |
| C：错误实体/枚举 | 多账户、多卡、相似交易及干扰对象 | 客户归属、目标对象集合、错误对象写入检查 |
| E：漏必填字段 | 使用当前实际 schema，不凭相似工具猜签名 | 缺参、多参；无参工具的 `{}` 不误判为缺参 |
| F：错误业务判断 | 生成批准与拒绝、等待与执行、可自助与必须升级等不同分支 | 从原始财务事实与政策独立推导，验证错误方向反例 |
| 工具都成功但终态错误 | 验证真实业务目标及副作用 | 漏写、错金额、重复写、额外写均必须被识别 |

### 5.1 工具协议：从“文字上知道”变成“每一步真的执行”

以报告中出现的提额提交工具为例，第一步是：

```json
{
  "name": "unlock_discoverable_agent_tool",
  "arguments": {
    "agent_tool_name": "submit_credit_limit_increase_request_7392"
  }
}
```

收到解锁返回后，再按其真实签名构造业务参数，调用 `call_discoverable_agent_tool`。其外层使用同一个 `agent_tool_name`，内层 `arguments` 是序列化 JSON 字符串。

这里有四个训练重点：**完整名字从公开证据取得、先看到解锁结果、再按实际签名填写、不能擅自增加参数**。本文不列固定业务参数模板，因为模型正应当读取实际返回，而不是机械背下另一种工具的字段。

普通公开工具不需要这套解锁流程。新版同时训练这种区分，避免把“所有工具都先 unlock”当成万能规则。

### 5.2 决策方向：针对 task_051 的“本该拒绝却批准”

新题让教师检查账户、申请历史、支付历史和相关状态，再依据政策决定是否批准。金额也必须区分“申请增加多少”和“最终额度是多少”。

高利用率边界采用成对任务：两题的客户、账户、其他随机参数相同，只改变初始余额，使利用率跨过政策边界，正确决定随之翻转。

这对题要教的是：“决定由证据变化引起”，而不是“用户要求提额时就批准”。检查器验证确实只有指定源字段改变；同一反转对进入同一数据划分，防止训练集与验证集各放一个近乎相同的成员。

### 5.3 对象覆盖和行动克制：该办的全办，不该办的不动

场景加入多个符合条件对象、相近但不符合条件对象和已处理记录。教师需要逐一识别，不能只完成第一项，也不能为了显得积极而重复写入。

例如，处理一笔有争议的交易不等于处理同账户全部交易；补换实体卡也不等于把整个信用账户关闭。检查既看目标状态，也看旁边那些本来不应改变的状态。

### 5.4 用户交接：发出指示不等于已经完成

新版区分三类工具：

1. agent 已有的普通工具；
2. agent 需要发现并解锁的隐藏工具；
3. 用户负责的工具，其中又有原本就拥有的普通工具，以及必须实际授予的隐藏工具。

隐藏用户工具的任务，要核对授予、工具名、ID、参数、数量以及真实用户执行结果。不能仅凭 assistant 说“请操作一下”就判完成。

但用户原本就有的 `submit_transaction` 等普通工具，不应被额外要求从 KB 发现或由 agent 授予。repair6 给审核器提供真实用户工具 schema 与调用记录，避免把正确用户行为误判为失败；这些用户专属信息不会塞进教师上下文。

### 5.5 升级：不仅要转人工，还要选对原因

此前一类征信事故题的公开文档说是银行后台批处理错误，生成目标却选择 `fraud_or_security_concern`。参考动作和目标一起写错，导致旧检查可以“自洽通过”。

repair6 改为与公开事故原因一致的 `technical_system_error`，并增加独立原因检查。检查全量 3,220 个实例时，有 57 个实例受影响，其中前 400 题有 8 个；它们不能直接沿用旧正向证书。

这个例子说明：**双模型通过和参考答案能执行，并不天然保证题目正确。** 还需要与公开业务事实独立核对。

## 6. 对早期 F1–F8 能力框架的承接

v03 的 A–G 是工具错误分类；最初报告的 F1–F8 是另一套能力归因，不能直接把同字母当成同一类。

| 早期能力标签 | 新版落到什么业务训练上 |
|---|---|
| F1/F3：发现与对象覆盖 | 原生文档检索、账户→卡→交易的查找、多对象办理 |
| F2：政策推导 | 提额资格、争议责任、利息收益、时间边界和例外条件 |
| F3b：用户工具交接 | 实际授予与实际执行；普通用户工具和隐藏工具分开判断 |
| F4：写入克制 | 已办理记录、非目标对象、重复入账和额外写入反例 |
| F5/F6：升级判断 | 可自助与必须转人工的业务分支、正确转接原因 |
| F7：签名遵循 | 解锁后使用实际字段、必填参数、枚举及 JSON 契约 |
| F8：行动与知识边界 | 信息充足就执行；缺信息先问；超范围按政策停止或升级 |
| 检索循环、长程执行 | 真实共享政策库、分散证据、跨对象依赖和多步任务 |

标签只是索引。只有对应机制实际进入任务，且错误做法会被检查拒绝，才算有覆盖。

## 7. 这次为什么还修了运行时和审核器

如果题目或环境有问题，生成更多教师轨迹只会放大问题。此次修复同时清理了以下干扰项：

| 问题 | 采取的措施 | 避免什么错误学习/误判 |
|---|---|---|
| 提额提交后批准重复插入同一申请 ID | 合成专用版本更新匹配的 PENDING 申请，先检查用户、账户、金额和状态 | 防止额度变了、申请却未正确批准 |
| 补卡误关闭账户 | 合成专用版本保留信用账户状态，由补卡订单记录旧卡取消 | 不把换卡学成销户 |
| 多账户补偿记录键冲突 | 记录键包含账户身份，同账户重复仍拒绝 | 防止第二张卡的合法补偿失败 |
| 历史支付早于开户时间 | 按日历和开户事实生成历史，并独立检查 | 不让教师在矛盾历史上做资格推理 |
| 争议任务缺必要事实 | 补足用户知道的购买渠道、账单日期、报案及处理意愿等 | 不把缺信息导致的询问误当能力差 |
| 开户跳过资格查询 | 增加写入前查询和独立时序检查 | 即使终态相同，事后补查也不能冒充合规 |
| 补卡参考答案多了无必要查询 | 移除非必要步骤，接受合法额外查询 | 避免只有机械复刻参考动作才得分 |
| 审核器不知道普通公开工具 | 提供实际初始 agent policy 和工具 schema | 不把文档没介绍的合法普通工具当幻觉 |
| 审核 JSON 或 assistant 编号错误 | 明确编号、严格 schema、对原轨迹有界重审 | 不因审核器格式错误重新抽教师“直到成功” |
| 征信事故原因与目标矛盾 | 用公开事故原因独立检查转接 reason | 不让错误目标与错误参考互相证明 |

这些运行时改动通过 `native_runtime.revision` 隔离，仅用于带相应标记的新合成任务；官方默认任务行为保持原样。环境差异会进入快照与版本证据，后续迁移效果仍需官方环境评测确认。

## 8. 怎样保证导出的数据值得训练

### 8.1 先检查题目，再检查教师答案

任务准入检查契约、数据、文档、目标、反例和公开可解性；教师成功率不反过来决定题目是否保留。

两模型独立盲解为准入提供证据，但不是要求两个模型都在线解成功才能留下题目。正常求解失败与基础设施错误也必须区分：前者可能是难题，后者是证据不完整。

内容确有错误的候选在同一配额内有界重建；有效但困难的任务不能通过换简单题掩盖。

### 8.2 每题四次，主集只收干净成功过程

- 四个不同 seed 预先固定，不能因为失败换 seed。
- GLM 教师温度 0.7，用户和审核温度 0；当前配置是 200 步、单轨迹 3,600 秒。后者是后来显式扩展的预算，不能拿它冒充原先 1,800 秒条件下的结果。
- 主集要求正常成功、质量通过，并且全程没有工具或协议错误。
- 最终成功但中途犯错的轨迹单独存入 `sft_recovery.jsonl`，错误 assistant 轮及其 reasoning 屏蔽，不混入主集产出率。
- 四次没有合格样本的有效题进入难题池，记录到底是环境失败、质量拒绝还是证据不完整。

`teacher_pass@4` 是至少一次环境成功的任务比例；`sft_yield@4` 是至少一次得到合格主集样本的任务比例。两者都不是训练后学生的官方通过率。

### 8.3 只学习模型当时真正看到和产生的内容

导出绑定实际 agent 上下文，保留工具 schema、用户消息、工具结果、assistant 文本与调用。只有应学习的 assistant 内容产生训练标签。

用户私有工具过程、gold、评分意见和独立盲解内容不拼入教师上下文。当前 `strict_preserve` 对教师实际产生的 reasoning 检查正确性、当时可见证据和私有信息泄漏；缺失的 reasoning 不补造。

每道题若有 k 条合格轨迹，清单给每条 `1/k` 权重，避免容易题因成功次数多而获得更大总权重。外部训练器必须真正使用该权重或等价的按 task 均匀采样，文件里写了权重不等于训练端已经执行。

tokenizer、模板、工具参数往返和 mask 都有检查。超长轨迹保留原始证据并标记拒绝，不偷偷截断成不完整成功故事。

## 9. 速度、恢复和预算做了什么

GLM 与 Gemini 共用 **256 个物理请求并发上限**。GLM 负责教师、候选生成和报告分析；Gemini 负责用户与质量审核；两者各自参与盲解和审核。因此不能把“教师使用 GLM”理解为“全流程调用数必然以 GLM 为多数”。

导出使用单槽位分片，再汇总成训练文件，避免每完成一条轨迹就反复重扫重写整批。产物通过 capture、审核证据和内容 hash 绑定，恢复时防止重复导出。

修复产生新版本，旧原始轨迹和失败记录保留。只有业务事实、目标、工具环境、模型参数与 seed 等满足一致性要求，并通过严格工具回包回放，才允许恢复原始证据。改变业务目标的任务不能直接套用旧证书。审核逻辑改变时也可能需要重新审核。

历史请求、失败、重试和 token 支出累计继承，不因开新目录清零。12000 次只是全量 3000 题的四次教师槽位；用户模拟、盲解和审核还会产生大量额外物理调用。

并发配置是上限，不是实时占用承诺。准入依赖、审核、导出、阶段锁和失败门槛都可能让实际并发低于 256；若阶段未完成，需要报告缺口，不能为了保持并发跳过验证。

## 10. 什么条件下才能说“可以量产”和“确实解决了报告问题”

目前采用的阶段是：

```text
20 题试跑
    → 400 题训练包 + 200 题结构隔离验证包
    → 外部实际 SFT + 同条件配对测评
    → 验证回执达标后扩至 3000 题训练池
```

这已经不同于最初“3000 题全部训练、不另建合成验证集”的设想：**3000 题仍全部属于训练池，另加 200 题验证**。400 题是冻结训练池的前缀；试跑默认不混入正式训练。

验证隔离按业务结构，不仅按姓名或客户 ID。官方测评已经参与课程设计，只能叫适应性开发反馈，不能声称是完全独立的留出验证。

要证明改进有效，需要锁定实际 base/candidate checkpoint、训练清单、网关、推理设置、任务及 trial 条件，检查：

- 官方整体分数是否提升；
- unlock/call 协议错误和幻觉工具是否下降；
- 第一次可发现工具调用格式是否更稳定；
- task_050–054，尤其 task_051 的决策是否改善；
- 是否以更多错误实体写入、额外操作或原有能力退化为代价；
- 结构隔离验证集是否同时改善。

教师能做对说明“有合格训练材料”，静态检查通过说明“检查范围内题目自洽”，只有重新训练后的可比评测才能说明“学生学会了”。三种证据不能互相替代。
