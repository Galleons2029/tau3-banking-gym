## 1. 领域概览：这个域到底在考什么

airline / retail / telecom 三个域把业务规则写在系统提示词里，工具是固定的一套。`banking_knowledge` 反过来：策略提示词只有一页通用守则，**所有业务规则、工具名、参数、前置条件、金额口径都埋在知识库文档里**，智能体必须自己检索出来。

因此这个域同时压测三种能力，而且它们是串联的——任何一环断掉，最终 DB 状态就对不上，奖励直接归零：

1. **检索**：从 698 篇文档里找齐这次任务需要的 1–30 篇（任务自带 `required_documents` 金标准清单，中位数 9 篇）。
2. **推理与核算**：按文档口径做比价、算返现、算利息、算 ATM 免费额度、判资格，结果精确到分。
3. **受约束执行**：把结论落成一串带前置条件的工具调用，且区分「自己调」「解锁后调」「交给用户调」三种通道。

### 任务集的基本形状

`data/tau2/domains/banking_knowledge/tasks/` 下 97 个 `task_*.json`。`tasks.json` 是同一份数据的合并文件。

| 维度 | 取值分布 | 说明 |
|---|---|---|
| 奖励基准 `reward_basis` | DB × 88，ACTION × 9 | 没有任何任务用 COMMUNICATE 或 NL_ASSERTION——`communicate_info` 全部为空 |
| 金标准动作数 | 1 – 37，中位数 9 | task_081 最长（37 步），A 族只有 1 步 |
| 必需文档数 | 1 – 30，中位数 9 | task_071 最多（30 篇），B/C 族最少（1 篇） |
| 带任务级初始状态 | 53 / 97 | 其余 44 个直接跑基线 `db.json` |
| 用户侧工具 | 80 个任务至少 1 个 | `apply_for_credit_card`×50、`call_discoverable_user_tool`×57、`request_human_agent_transfer`×19、`submit_referral`×6、`submit_transaction`×1 |

> **一个容易被忽略的设计**
>
> A 族 7 个「推荐信用卡」任务的金标准动作只有一条 `apply_for_credit_card`，而且 `requestor` 是 **user**。智能体根本没有这个工具——它只能靠对话把结论说清楚，让用户模拟器自己去调。**这实质上是用数据库状态来判「你有没有讲对」**：卡种、年收入、Rho-Bank+ 订阅这些参数一旦不符，DB 哈希就对不上。

## 2. 环境构造

环境由 `get_environment()` 在每个任务开始时现搭一次，四块拼起来：只读知识库、可变事务库、三层工具、按检索变体拼装的策略提示词。

### 2.1 双库结构

**知识库（只读，不进哈希）**：`data/.../documents/` 下 698 个 JSON，每个是 `{id, title, content}`，content 为 Markdown 政策片段。按前缀分 9 个类目：

| 文档族 | 篇数 | 内容 |
|---|---:|---|
| `credit_cards` | 110 | 个人卡产品条款、争议流程、销卡、提额、补卡 |
| `checking_accounts` | 110 | 支票账户各等级费率、ATM 免费额度、借记卡 |
| `savings_accounts` | 89 | 储蓄利率、分层、关联加成 |
| `business_savings` / `business_credit` / `business_checking` | 82 / 79 / 79 | 对公产品线（口径与个人线不同，是常见混淆点） |
| `everyone_pay` / `buy_now` | 51 / 48 | 支付与先买后付 |
| `bank_accounts` | 47 | **内部操作手册**——大部分可发现工具的说明书在这里 |
| `personal_subscriptions` / `customer_support` | 2 / 1 | Rho-Bank+ 订阅、转人工 |

**事务库（可变，进哈希）**：`db.json` 加载为 `TransactionalDB`。初始文件含 17 张表，模型共定义 22 张。关键表初始行数：`users` 39、`accounts` 33、`credit_card_accounts` 38、`credit_card_transaction_history` 338、`bank_account_transaction_history` 266、`payment_history` 18、`referrals` 19、`debit_cards` 8。空表如 `cash_back_disputes`、`credit_limit_increase_requests`、`debit_card_orders` 正是任务要写进去的地方。

另有三类表是**纯粹为评分而存在的行为日志**：`verification_history`（身份核验审计）、`agent_discoverable_tools`（智能体调用过哪些可发现工具）、`user_discoverable_tools` / `user_discoverable_tool_calls`（发给用户的工具和用户的调用）。它们同样参与哈希，所以「有没有按流程走」是能被 DB 判分抓到的。

### 2.2 三层工具

| 层 | 数量 | 可见性 | 代表 |
|---|---:|---|---|
| 智能体常驻工具 | 14 | 系统提示词中始终可见 | `get_user_information_by_*`、`get_current_time`、`log_verification`、`transfer_to_human_agents`、`change_user_email`，以及三个元工具 |
| agent 可发现工具 | 48 | **不可见**，须从知识库读出名字后解锁 | 34 个写工具 + 11 个读工具 + 3 个场景转人工工具 |
| 用户常驻 / 可发现工具 | 6 / 4 | 用户模拟器持有；可发现的须由智能体下发 | `apply_for_credit_card`、`submit_referral`、`request_human_agent_transfer`；`submit_cash_back_dispute_0589`、`get_card_last_4_digits`、`deposit_check_3847`、`get_referral_link` |
| 检索工具 | 按变体 | 随 `--retrieval-config` 注入 | `KB_search_bm25`、`KB_search_dense`、`grep`、`shell` |

### 2.3 可发现工具机制（本域的核心设计）

48 个业务工具全部带 `_四位数字` 后缀（`file_debit_card_transaction_dispute_6281`、`open_bank_account_4821`…），后缀是刻意的：**猜不出来**。工具名、参数枚举、前置条件只出现在某一篇知识库文档里，智能体必须检索到那篇文档，才谈得上调用。

```
知识库文档  ──检索──▶  unlock_discoverable_agent_tool(name)
doc_bank_accounts_…_031      返回参数签名，仅写内存，不入库
                                      │
                                      ▼
                          call_discoverable_agent_tool(name, args)
                          未解锁则报错拒绝；数字参数统一归一为 float
                                      │
                        ┌─────────────┴─────────────┐
                        ▼                           ▼
                业务表写入                  agent_discoverable_tools
        disputes / orders / accounts …   写工具全记；读工具仅白名单内记
                        └─────────────┬─────────────┘
                                      ▼
              两条路径都进入最终 DB 哈希 —— 走错通道、漏解锁、参数写错都在这里暴露
```

对称地，`give_discoverable_user_tool` 把工具下发给用户，用户再用 `call_discoverable_user_tool` 执行——**智能体不能代劳**。

策略提示词对这套机制加了两条硬约束，二者都直接影响判分：**「不要解锁你并不打算真正使用的工具」**（会污染日志表），以及**「工具名和参数只能来自知识库，不许臆造」**。

### 2.4 检索配置：同一批任务，20 种难度

`--retrieval-config` 决定智能体拿到什么检索能力，默认 `alltools`。这一维是这个域最有意思的消融轴：任务不变，只换知识获取方式。

| 变体 | 注入的工具 | 依赖 | 用途 |
|---|---|---|---|
| `no_knowledge` | 无 | 离线 | 下界：证明任务确实需要知识库 |
| `full_kb` | 无（698 篇全文塞进提示词） | 离线 | 长上下文上界 |
| `golden_retrieval` | 无（只注入 `required_documents`） | 离线 | **完美检索上界**——摘掉检索误差，只看推理与执行 |
| `bm25` / `openai_embeddings` / `qwen_embeddings` | `KB_search` | 离线 / `OPENAI_API_KEY` / `OPENROUTER_API_KEY` | 经典 RAG；可加 `_reranker`、`_grep` 后缀组合 |
| `grep_only` | `grep` | 离线 | 纯词面检索 |
| `terminal_use` / `_write` | `shell` | sandbox-runtime | Agentic search：在沙箱里 ls/cat/grep 翻文档目录 |
| `alltools`（默认）/ `alltools-qwen` | `KB_search_bm25` + `KB_search_dense` + `shell` | 嵌入 API + sandbox-runtime | 排行榜口径 |

> **环境陷阱**：`shell` 依赖 `srt` / `rg` / `bwrap` / `socat`。自 1.0.x 起缺依赖会在构造期抛 `SandboxRuntimeError` 直接失败——早期版本是把「沙箱不可用」当成普通工具返回值喂给智能体，导致它学会放弃调用工具，分数被静默压低。跑基线前先 `which srt rg bwrap socat`。

### 2.5 任务级初始状态与开关

53 个任务带 `initial_state.initialization_data.agent_data`，向 DB 注入该场景专属的用户、账户、卡片、交易流水（典型 7 KB 左右）。评测时这份数据会同时注入「预测环境」和「金标准环境」，保证两边同起点。

task_026–029 用了一个更精巧的开关：`task_config.dispute_settings.auto_resolve_disputes`。026/028 为 `true`、027/029 为 `false`——**同一个用户、同一个场景，只因环境侧的争议是否自动结案，正确动作序列就从 6 步变成 11/15 步**（后者要求智能体额外用 `update_transaction_rewards_3847` 手动改正返现）。这是在考「按环境反馈调整策略」，而不是背流程。

### 2.6 确定性 ID

所有新记录的主键都由 `sha256(业务字段拼接)` 截断生成（`generate_dispute_id`、`generate_referral_id`、`generate_bank_account_transaction_id`…）。这是 DB 哈希比对能成立的前提：只要业务参数一致，无论谁在什么时候调用，记录 ID 都一样。反过来说，**任何一个业务参数写错，都会生成一个不同的主键，DB 直接不匹配**。v1.0.1 专门修了整数/浮点写法（`25` vs `25.0`）导致 ID 分叉的问题。

## 3. 交互过程

半双工（回合制）文本模式，由 `Orchestrator` 驱动三方：用户模拟器、智能体、环境。

```
仿真阶段
Task JSON ──▶ get_environment() ──▶ ┌ 回合循环 (max_steps 200 / max_errors 10) ┐ ──▶ 轨迹
scenario      建库+拼工具+拼策略      │  用户模拟器 ⇄ 智能体                     │    messages
initial_state                        │      ↓ user tools   ↓ agent tools        │    + tool calls
                                     │        环境 / 工具                        │    termination
                                     └──────────────────────────────────────────┘

评分阶段
预测环境 (新建 + 回放智能体轨迹)  ┐
                                  ├─▶ get_db_hash() 比对 ─▶ reward ∈ {0,1}
金标准环境 (新建 + 回放 golden)   ┘    agent 库 + user 库    各分量按 reward_basis 连乘
                                       全等才得 1.0
```

### 3.1 一个回合里发生什么

1. **初始化**：注入 `initialization_data`，回放 `initialization_actions` 与 `message_history`。
2. **用户先说话**。用户模拟器拿到的是任务的 `user_scenario.instructions`（一段第二人称角色剧本）加全局模拟守则，被明确要求「不要一次性倒出所有信息，只在被问到时提供」。
3. **智能体回合**：可以说话，也可以发工具调用。检索工具、常驻工具、`unlock`/`call_discoverable` 都在这里发生，工具结果回灌后可以继续调用，直到它选择说话。
4. **用户回合**：除了说话，用户模拟器也可能调用自己的工具（申请信用卡、提交推荐、执行智能体下发的可发现工具、请求转人工）。**这些调用同样写入数据库、同样参与判分。**
5. **终止**：用户发出 `###STOP###` / `###TRANSFER###` / `###OUT-OF-SCOPE###`，或智能体发出 `###STOP###`，或触顶 `max_steps=200` / `max_errors=10` / 超时。

> **先决条件**：只有以 `AGENT_STOP` 或 `USER_STOP` 结束的仿真才会被评分。`MAX_STEPS`、`TOO_MANY_ERRORS`、`TIMEOUT` 一律直接 **reward = 0**，连 DB 都不比。这对 L 族（22–37 步金标准）是实打实的压力——步数与上下文预算本身就是考点。

### 3.2 智能体侧的通用守则

系统提示词由 `policy_header` + 检索工具说明 + `additional_instructions` 拼成。除了可发现工具的用法，其中有两条会被任务反复触发：

- **身份核验**：凡是要读写用户数据，必须先让用户答对「出生日期 / 邮箱 / 电话 / 地址」四项中的任意两项；姓名和 user ID 不算。核验通过后必须调 `log_verification` 写审计记录。核验前不得泄露任何用户信息。*97 个任务里 81 个的金标准包含 `log_verification`。*
- **转人工的门槛**：只有确认知识库和策略里都没有可行动作时才转；转之前要先问用户；用户主动要求转人工时先尝试自助，**要求满 4 次**才可以转。知识库中的场景专属规则可以覆盖这条。

| 默认参数 | 值 | 来源 |
|---|---|---|
| max_steps / max_errors | 200 / 10 | `src/tau2/config.py` |
| 默认 agent / user LLM | `gpt-4.1-2025-04-14` | 可用 `--agent-llm` / `--user-llm` 覆盖 |
| 温度 | 0.0 / 0.0 | agent / user |
| seed / 并发 / 轮次 | 300 / 3 / 1 | pass^k 需要 `--num-trials > 1` |

## 4. 评估标准

最终奖励是 `reward_basis` 中各分量的**连乘积**，每个分量都是 0/1。这个域只用到两种分量，而且互斥：88 个任务用 DB，9 个用 ACTION。

### 4.1 DB 分量：端状态哈希比对（88 个任务）

最容易被误读的一点：**`evaluation_criteria.actions` 不是对智能体的动作要求**，它只是「一条能解决问题的参考轨迹」。评测器的做法是：

1. 新建一个环境，注入 `initialization_data`，把**智能体轨迹里的所有工具调用**回放一遍 → 预测端状态；
2. 再新建一个环境，同样注入初始数据，把 **golden actions** 回放一遍 → 目标端状态；
3. `get_db_hash()` 与 `get_user_db_hash()` 两边都全等，DB 分量记 1.0，否则 0.0。

所以路径自由、顺序可换、只读工具可多可少（见下），但**写进数据库的每一条记录、每一个字段、每一分钱都必须一致**。这是一个极其严格的全或无判据。

> **read_log_allowlist —— 一个必须知道的细节**
>
> `call_discoverable_agent_tool` 会把调用记进 `agent_discoverable_tools` 表，而这张表进哈希。若不加处理，智能体出于谨慎多做一次只读校验（比如开户后再查一遍账户列表）就会让哈希分叉、奖励归零——而知识库恰恰鼓励这么做。
>
> v1.0.1 的修法是：**写工具的调用一律记录；读工具只有出现在该任务金标准里时才记录**（白名单由 `_derive_read_log_allowlist(task)` 从 golden actions 提取）。这样「必须查这个才能继续」的断言仍然有区分度，多余的只读校验则被忽略。这一项修复贡献了 1.0.1 中几乎全部的分数变动（GPT-5.5 xhigh: 37.37 → 46.39）。

### 4.2 ACTION 分量：逐条动作匹配（9 个任务）

task_004 / 008 / 012 / 014 / 032 / 033 / 034 / 035 / 083 改用 ACTION：金标准里的**每一条动作都必须在智能体（或用户）的工具调用中找到匹配**，全中才记 1.0。匹配范围由 `compare_args` 控制：

- 004 / 008 / 012 / 014：`compare_args=["reason"]`——只比转人工的 `reason` 枚举值，摘要文本不比。
- 032 / 033 / 035：比 `agent_tool_name`，要求正确解锁并调用场景专属的转人工工具。
- 034：`compare_args=[]`，只要求出现 8 次用户 `request_human_agent_transfer` 与 1 次 `transfer_to_human_agents`，不比参数。
- 083：`compare_args=None`，**全参数精确匹配**，包括 4 笔争议的完整 JSON 参数串——这是全域最严的一个。

为什么这 9 个不走 DB？因为它们的正确结局大多是「什么都不做，转人工」，端状态几乎不变，DB 判据没有区分度；而 083 要考的正是「有没有逐个解锁到位」，解锁本身不写库。

### 4.3 汇总指标

标准指标是 **pass^k**：同一任务跑 `num_trials` 次，`pass^k` 是「随机抽 k 次全部成功」的概率估计，因此 pass^1 就是平均奖励，k 增大衡量稳定性。框架同时统计读/写动作命中率、DB 匹配数、身份核验成功/失败数、各终止原因分布——排查失败时先看这些。

> **版本兼容性**：`banking_knowledge` 的分数在 v1.0.1 前后**不可比**。除白名单修复外还有三处：数值参数整/浮点归一化（#397）、`get_bank_account_transactions_9173` 改为倒序返回（#403，否则「争议最早那一笔」的规则无法从工具输出判定）、task_074 金标准退费由 $8.00 更正为 $14.50（#374，这一项会让旧的通过轨迹变成失败）。旧结果可用 `tau2 evaluate-trajs --fresh-tasks` 重打分；要复现旧行为需 pin `pre-v1.0.1` 标签。

### 常见的归零原因

- 金额算错一分（K、O、E 族高发）——哈希不匹配。
- 业务参数拼错导致确定性主键分叉（例如 dispute 的 `dispute_category` 选错枚举）。
- 解锁了却没用的工具，或该由用户调用的工具被智能体自己调了。
- 漏 `log_verification`，或在核验前就泄露了用户信息。
- 长任务触顶 `max_steps`，仿真被判无效。
- 该拒绝时照做了（B、H、I 族的对抗性用户专门设计来诱导这一点）。

## 7. 复现

### 跑一次完整评测

```bash
tau2 run --domain banking_knowledge \
  --retrieval-config alltools \
  --agent-llm <model> --user-llm gpt-4.1 \
  --num-trials 4
```

省略 `--retrieval-config` 时默认 `alltools`（需要 `OPENAI_API_KEY` 与 sandbox-runtime）。要完全离线，用 `--retrieval-config bm25`。做检索能力消融时，`golden_retrieval` 与 `no_knowledge` 是两个有用的端点。

### 重打分历史轨迹

```bash
tau2 evaluate-trajs --fresh-tasks <results.json>
```

会应用当前版本的任务数据与 `read_log_allowlist`，是把 < v1.0.1 的结果搬到新口径的唯一正确方式。

### 关键源码位置

- 任务数据 — `data/tau2/domains/banking_knowledge/tasks/`，文档 — 同目录 `documents/`，基线库 — `db.json`
- 环境装配 — `src/tau2/domains/banking_knowledge/environment.py`
- 48 个可发现工具与元工具 — 同目录 `tools.py`
- 检索变体注册表 — 同目录 `retrieval.py`（`RETRIEVAL_VARIANTS`）
- 判分 — `src/tau2/evaluator/evaluator.py`、`evaluator_env.py`、`evaluator_action.py`
- 读白名单推导 — `src/tau2/runner/build.py` 的 `_derive_read_log_allowlist`
- 官方说明 — `docs/evaluation.md`、`src/tau2/knowledge/README.md`、`CHANGELOG.md`
