# r10 repair4：开户资格查询与原轨迹恢复

本版接续 `targeted-native-v03-r10-repair3`，修复双模型准入发现的开户资格检查缺口。
repair3 的两道补卡题均通过双模型审核，八次教师采样全部成功并合格；其最终结果为
19/20 道有效任务、76/80 个完整计划槽位、38 条环境成功轨迹、36 条合格导出。
该版没有启动 400 题正式阶段，原始证据全部保留。

## 缺陷与范围

个人 checking 开户政策要求先确认已有账户数量和近期因故关户等资格条件。
短开户生成器只有身份验证、解锁开户和开户三个动作，既没有查询，也不能拒绝
跳过资格检查的执行路径。第 19 题收到审核异议；检查同一机制确认第 15 题也受影响。

历史轨迹与任务契约的缺陷需分开看。`account-eligibility-diagnosis.json` 逐行绑定
此前四版受影响试跑导出：8/7/7/4 条分别都出现了开户前查询本客户账户的调用。
这不能把有缺口的任务验证器判为正确，也不支持宣称这些教师轨迹都漏查了资格。
原文件不改写；所有试跑数据原本就不混入正式训练池。

## 修订

1. 显式开户配方先调用真实的账户查询，再办理开户。包含完整 unlock/call 流程的
   开户参考至少五步，不再归入 1–4 桶。正式配方保留开户操作覆盖要求。
2. 新课程的短账户服务使用客户明确请求的邮箱更新；类别和动作难度总配额不变。
   旧课程的生成器契约保持原样。当前试跑只有第 15、19 题的业务操作发生变化。
   短任务不追加旧版开户子流程；邮箱字符串变化不计为新的政策结构。只有一种结构
   的邮箱更新场景归训练，验证配额由其他真实结构承担。
3. 新课程中每个开户目标独立要求成功查询本客户账户早于成功开户；允许合法重复
   查询。增加漏查、查询其他客户、开户后查询的反例。后两类不能仅依靠终态 DB
   判断，特别验证“DB 相同但业务义务不满足”的路径被拒绝。
4. 复用补卡或 statement credit 轨迹时，先检查业务运行时文件 hash 及版本。
   字节和版本均未变化时允许复用，并继续严格回放原始工具结果；变化时保留排除规则。
   不修改成功/失败原始记录，不更换四个固定 seed。
