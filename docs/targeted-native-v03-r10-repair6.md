# r10 repair6：事故转接原因、用户工具审核与正式证据恢复

> 状态更新（2026-09-19）：repair6 已于 19:07 自动启动，19:25 因试跑第 6 题的公开可解性审核异议停止。下文为交接前设计记录；后续处理见 [repair7](targeted-native-v03-r10-repair7.md)。

本版针对 repair5 正式生成中发现的两个问题。当前生产源码仍为 repair5；修复先在隔离副本
完成检查，再由 `repair6-preflight/activate-after-generation.py` 在现有阶段释放轮次锁后接续。
运行状态以 `data/synthesis/targeted-native-v03-r10-repair6-preflight/activation-state.json` 为准。

## 已确认的问题

征信事故公开文档明确写明银行后台批处理错误。生成器却把该事故的转接原因写为
`fraud_or_security_concern`，与转接原因政策中的 `technical_system_error` 冲突。
参考动作和目标同时错误，因此旧正反例可以自洽地通过，甚至存在旧双模型均通过的任务。
新检查从公开事故原因独立检查目标及参考动作，能拒绝这种错误。

对全部 3220 个实例的新旧编译对照发现，修复改变 57 个征信事故实例的业务目标，
其中 400 题训练前缀有 8 题：38、75、115、159、167、177、182、253。
业务结构分组没有变化；配额、难度和四个固定种子不变。旧版相关任务的正向准入证书
不能覆盖这一内容缺陷，旧训练包在修复前不得使用。原始证明、轨迹和评分保留。

另一项异议来自第 192 题：审核器将用户本来就拥有的普通 `submit_transaction` 工具
误当作需要从 KB 发现并由 agent 授予的隐藏工具。实际盲解成功，用户通过自己已有的
工具完成购买，agent 查询实际交易。修复给私有审核输入补充运行时真正提供给用户的
工具 schema 和实际用户工具调用，区分普通用户操作与隐藏工具交接；不向教师提供这些
用户专属 schema，也不改变隐藏工具的发现、授予和调用要求。

## 恢复与阶段交接

新增显式 `reuse_parent_splits`，可以复用已准入、未变化的训练和验证任务原始轨迹。
沿用客户事实、业务目标、完整任务、公开环境、模型设置和种子一致性检查，以及工具
回包严格回放。成功、失败原样保留。已改变目标的事故任务不复用旧轨迹。

业务检查逻辑改变后，旧双模型审核结论不直接沿用；恢复原始盲解后重新审核。
教师轨迹仍经过当前评分和质量审核。预算继承原父轮全部已消耗调用、token 和采样次数，
不会把复用的历史调用当作新的免费采样，也不会把历史花费清零。

持久交接进程等待现有 `round.lock`，确认 400 个生成槽位均已有结果、索引完整、共享池
没有活跃请求，再结束旧监督器及其待启动子进程。它逐文件检查源码与修复证明的 SHA256，
发现并行修改就停止交接并明确报错。随后创建 repair6 配置、导入绑定来源的失败画像、
继承最终预算并启动原监督器，继续 20 题试跑、400 题采样导出及 200 题验证包。
全量 3000 题阶段仍须外部训练和配对评测回执。

曾额外启动一次 collect 入口以尝试提前采样；源码检查确认该入口等待整轮锁，尚未启动
任何采样即已撤掉。现在只有监督器负责阶段调度，记录保存在 repair5 的
`live-collect-01-resolution.json`。
