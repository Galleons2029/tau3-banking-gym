**当前批次 SFT 后退化：证据核查与下一轮改进方案（2026-09-17）**

本分析使用两份 gw134 失败报告、截图、三个测评目录的原始轨迹、当前合成批次冻结生成器和实际导出文件。用户已确认：`tau3_banking_dots3_max` 是训练前基线，omni-preview 与 note-oi-stage2 都是训练后结果。分析没有修改测评结果、任务、生成器或训练代码。

核心判断：当前合成数据在自建 V2 环境内有效，但对官方银行业务的覆盖和协议一致性不足。七个能力标签并不等于七套完整的银行业务流程；实际训练数据主要覆盖同一类案例更新。用户随后确认三组运行的实际推理配置一致，reasoning_effort 是无效提示参数；下表保留日志字段供追溯，不把这些字段差异当作退化原因。网关解析、训练文件版本和报告口径仍需依据实际证据核查，不能据此直接增加同类数据量。

**二、原失败分析中必须纠正的归因**

1. **117 次不是同一口径的 Python 硬错误。** omni 的 117 次由 `error=True` 和工具返回的 `Error:` 文本共同构成，包含正常业务拒绝。真正 `error=True` 的工具结果分别为：基线 9/12449、omni 25/2564、stage2 23/2606。基线只数异常标记、训练后却数全部错误文本，不能得出“硬错误暴涨 60 多倍”。按前一统一口径，工具结果异常率约为 0.072%、0.975%、0.883%。

2. **未 unlock 调用是训练前已有的问题。** 三组分别有 244/485、53/97、51/97 次，即平均每 trial 约 0.50、0.55、0.53 次。它值得修复，但不是本次新增退化的主要证据。相反，进一步排除“账户/交易对象不存在”后，工具不存在或调用入口错误为 19/485、15/97、35/97，按 trial 归一后明显上升。这里也包括把真实存在的标准工具错送到 discoverable 入口，不能全部称为凭空捏造工具名。应追踪名称来源、入口选择和协议序列化。

3. **697 个检查项中 346 个 unmatched 的统计可以复现，但它不是 346 个独立业务根因。** 同一个 wrapper 名称可能封装查询、更新、交接等不同操作；预期包装调用与实际直接调用也会不匹配。必须把 wrapper、真实操作、actor、对象、参数和成功结果拆开。`call_discoverable_agent_tool` 被标记 WRITE，并不代表里面每次实际执行的都是业务写入。

4. **task_055 不是“完全没开户”。** stage2 直接调用了两次 `open_bank_account_4821`，分别开立 Purple Account 和 Silver Plus Account，参数与 golden 的两个开户操作一致，工具明确返回成功。其缺少预期 wrapper 路径，同时用户存款有先错误参数/未授予尝试、后续授予再执行的过程。该案例需要做完整 DB diff，不能用包装层 action mismatch 推导“账户未创建”。

5. **DB 不匹配不必然只来自业务状态。** 该次测评 commit 的包装调用会向 `agent_discoverable_tools` 写入 CALLED 记录；直接调用底层工具可能完成业务更新，却缺少这类记录。DB diff 应区分业务表、身份验证/交接/工具调用记录以及参数序列化产生的标识差异。官方总分仍按原规则报告，诊断分层不意味着放宽正式评分。

6. **task_039 是错误参数与框架报错质量问题叠加。** 模型把 `tool_name` 传给要求 `agent_tool_name` 的 wrapper；`Environment.make_tool_call(message.name, **message.arguments)` 随后触发同名参数冲突。因此不能全归咎于模型，也不能说模型参数没有错误。应改善边界校验，使它返回明确签名错误，而不是悄悄把参数改对。

7. **不能把所有数字字符串问题归因于 SFT。** 当前 8179 行中，动态业务 `amount` 参数 24135 次，仅 50 次为字符串，其余为 int/float；布尔约束在 V2 中也是严格布尔。omni 的部分直接工具调用/原生格式解析确有类型错误，但不足以支持“教师几乎都用字符串教参数”的说法。

8. **行为相关不等于原因。** 更多检索并不能证明检索导致失败；两个模型犯同样的政策错误也不能证明 KB 一定有错。优先检查适用条件是否齐全、引用是否匹配对象、政策计算是否正确，再判断文档是否矛盾。不要通过修改政策答案迎合失败轨迹。

**三、当前训练数据实际教了什么**

当前 formal/sft.jsonl 有 8179 行，来自 2679 个获得合格轨迹的独立任务，而不是 8179 个独立业务实例。每题贡献 1/2/3/4 行的任务分别为 185/503/976/1015 个。2944 个有效 task 中，剩余任务没有合格 SFT 行。按成功轨迹均匀采样，会使一题四成功的任务比一题一成功的任务获得四倍曝光。

| 主配方 | SFT 行数 | 实际主要机制 |
|---|---:|---|
| discovery | 1463 | 查询案例对象并逐个更新 |
| policy | 2115 | gross×rate/100+bonus、日期责任分档 |
| handoff | 758 | 将案例更新交给用户执行 |
| restraint | 1441 | 跳过已办理对象、防止重复更新 |
| escalation | 1083 | 根据 issue 写入 route 字段 |
| signature | 688 | 相近操作参数差异，包含 service_code |
| boundary | 631 | 缺少收据时写 awaiting_information |

生成器的实际结构是 accounts/cards/cases，1–2 个账户、对应卡、1/2/3/4/7 个目标案例和一个干扰案例。主要操作统一设置 `processed/adjustment/liability/route/delivery`；政策金额共享一个简单公式，业务选择经常可直接依赖 `eligible/service_kind/issue` 字段。

因此，当前“长程”主要是重复对象与查询分页变长，缺少真实银行工作流中的条件依赖和状态转换，例如：核验身份 → 调查可疑交易 → 判断卡是否应关闭 → 关闭旧卡 → 检查已有换卡订单 → 选择配送和费用 → 补卡 → 用户执行后续步骤。

已确认的分布差异：

| 维度 | 当前 V2 SFT | 官方评测 |
|---|---|---|
| agent wrapper 选择器 | capability | agent_tool_name |
| user wrapper 选择器 | capability | discoverable_tool_name |
| give-user-tool | capability，具体参数通常经自然语言交接 | discoverable_tool_name，可同时提供 arguments |
| 客户识别 | find_customer(email) | 多种身份查询、核验、log_verification |
| 时间 | 世界日期 | 精确模拟时钟及核验记录 |
| 升级 | 更新案例 route | 真正调用 transfer_to_human_agents 并选 reason |
| 业务结果 | 案例估算/办理标记 | 开户、关闭、资金、权益、争议、换卡等不同表和副作用 |
| 文档与流程 | 小型生成世界、统一结构 | 多产品、多政策、历史记录、相似流程竞争 |

8179 行中有 58486 次 agent wrapper 调用，其中 58483 次使用 capability。顶层实际工具集合只有 7 个；没有 log_verification、transfer_to_human_agents 或真实开户/转账业务调用。七个失败标签虽然存在，对官方对应业务能力的训练覆盖却不充分。

但也要避免过度归因：训练后官方轨迹的 wrapper 多数仍使用正确的 agent_tool_name，没有观察到大量直接复制 capability 的现象。因此协议分布不一致是已证实的数据问题和应修项，尚不是解释所有降分的已证实因果。

**四、文件、reasoning 与监督目标的风险**

当前存在两个不同导出版本：

| 文件 | 行数 | reasoning |
|---|---:|---|
| formal/sft.jsonl | 8179 | 默认不含供应商 reasoning |
| formal/general_agent_reasoning.jsonl | 8105 | 额外回填原始教师 reasoning_content |

general_agent_schema_audit.json 对第二个文件的结构审核为 PASS：103353 条 assistant 消息中有 74418 条带 reasoning。实际文件中 reasoning 共约 6265 万字符，可见 assistant 文本约 2307 万字符，前者约为后者 2.7 倍；这里不包含工具调用参数字符，不等于完整监督 token 占比。

原始文件的 loss_mask、转换文件的 loss 均符合 assistant-only；这仅能证明文件层面的标记正确，不能证明训练加载器正确采用了这些标记，也不能证明 tokenizer/chat template 保留了工具调用和 turn 边界。当前尚未确认训练实际用了哪个文件及其二次转换版本。

额外 reasoning 的语义质量没有被原先的成功轨迹质量审核同等验证。若实际训练使用该文件，需要单独检查：是否参与 loss、是否与目标模型原生思考格式兼容、是否被包装成普通回答、是否截断、是否造成较长教师推理风格的过度模仿。不能把有 reasoning 的转换文件仅凭 schema PASS 视为“与原始 SFT 完全等价”。

72 条最终合格轨迹含有 84 次可在 native 记录中确认的中间工具错误；当前 assistant 回合全部参与监督。这种轨迹可以提供恢复能力，但应把错误调用保留在上下文中、将错误动作本身的 loss 设为 0，只训练正确恢复与后续执行。修改时需要同步调整当前导出器“所有 assistant 都必须 loss=True”的约束，不能只改 JSON 标志而忽略加载链路。

已有导出完整性检查有价值，但它证明的是“可见上下文完整、调用配对、结果成功”，没有证明“每个被监督动作都是最佳动作”“教师推理正确”“训练到目标模型后会提高官方表现”。

新任务的负例不能只在最后金额减一或漏一条写入。必须包含“所有工具都执行成功、但选错整条业务路径”的反例：把正式争议错做成直接改奖励，把疑似盗刷错做成重置 PIN，把现金收益最优错做成按用户职业推荐。只有这类反例能检验现有最重要的静默错误。

**六、下一版合成方案：以官方契约和业务结构为主线**

这是对上一版纯能力迁移路线的调整建议，尚未实施。

1. 建立版本化的 banking 原生执行后端。读取明确版本的种子 DB、公开工具契约和政策快照；生成新的客户、账户、卡、交易、订单、争议和推荐实例，维护外键、历史状态与跨用户关系。Worldgen-V2 继续负责候选构造、证书、反例和审计，但主要训练任务在这个后端执行。不要只把旧 JSON 里的 capability 替换成 agent_tool_name：身份验证、用户授予参数和终态副作用也必须真实发生。

2. 同时固定 db_snapshot_hash、policy_hash、public_tool_schema_hash、runtime_hash、generator_version。用户/账户/交易 ID 的改写须覆盖全部关联字段。政策、商品和参数可以分层参数化，但同一任务的文档、工具与初始状态必须一致；不能抽象成另一个不具备实际银行流程的案例更新系统。

3. 任务从业务依赖图产生，而非先指定动作数。图节点区分信息获取、条件判断、参数推导、客户确认、agent 写入、用户写入、结果验证；边表示真实依赖。长任务必须包含多个相互影响的决策和状态变化，不能靠重复 unlock 或相同更新增加长度。

4. 保留成对边界任务：只改变一个事实，使正确流程或参数翻转。对象中同时包含未处理目标、已处理目标、相近但不合条件的对象。每个目标对象应记录选择/排除理由供私有验证；教师只能通过正常公开上下文推导。

5. 教师执行仍固定四个 seed。新任务、新运行预算、新审核协议使用新实验版本；不重采旧超时槽位来覆盖旧指标。独立盲解失败与任务本身无效分开，模型失败不作为自动替换困难任务的理由。

建议先为 300–500 个新任务做训练实验，确认有效后再冻结 3000 个正式任务的配额。可供首轮验证的业务配额如下，属于待实验调整的初始建议：

| 业务族 | 占比 | 3000-task 对应数量 |
|---|---:|---:|
| 多对象争议/返现处理及路径选择 | 25% | 750 |
| 借记卡诊断、限额、冻结、关卡补卡 | 20% | 600 |
| 开户/关闭与资金依赖 | 15% | 450 |
| 产品收益、推荐、APY/补款计算 | 15% | 450 |
| 身份核验、时间与 ID 精确保持 | 10% | 300 |
| 用户侧工具交接与执行覆盖 | 10% | 300 |
| 升级/知识边界 | 5% | 150 |

协议、枚举、检索、对象覆盖、写入克制作为横切属性，不能只落在单独某个配方里。独立的训练混合维度可先试“70% 新原生业务实例、20% 既有能力保持数据、最多 10% 旧 V2/跨场景探索”，并做比例消融；这些比例是实验起点，不是保证提升的结论。能力保持数据应覆盖基线擅长的产品选择、推荐、核验和合规自助操作，也应保留必要的通用工具能力。

官方 97 个任务已经参与训练设计，是适应性开发反馈。避免直接把其 golden 轨迹作为模板反复改写，再声称官方成绩是独立泛化结果。另建不同客户状态、对象图、政策条件组合的验证实例，按业务实例/图族切分；新增验证集不需要从原 3000 个训练任务中扣除。

**七、训练与导出的最小消融矩阵**

先确认基础 checkpoint、两个训练后 checkpoint、实际训练文件哈希、训练样本清单、加载器、chat template/tokenizer、训练步数、学习率、epoch、截断长度、packing、混合比例、loss mask、reasoning 策略。没有这些信息，不应断言学习率过大、灾难性遗忘或 reasoning 污染已经发生。

| 实验 | 目的 |
|---|---|
| E0：未 SFT 基线，统一当前服务与推理配置 | 在已确认推理一致的前提下，固定外部训练对照和服务版本 |
| E1：同一基线 + 当前数据，不监督教师 reasoning | 测量当前业务样本本身的收益或伤害 |
| E2：同一业务实例/可见轨迹 + reasoning | 分离额外 reasoning 的作用 |
| E3：同一基线 + 原生协议和状态完整的新任务 | 测量执行环境一致性和真实业务覆盖的收益 |
| E4：E3 加能力保持数据，并按任务/失败机制加权 | 测量保持旧能力和调整曝光分布的收益 |

E1/E2 必须对齐实际业务样本，不能直接用 8179 行对比 8105 行并把差异都归因于 reasoning。主比较固定可见动作曝光和训练设置，报告 reasoning 增加的监督 token；必要时另加等总 token 预算对照。

初期使用小步训练和多个中间 checkpoint。尚未拿到实际优化器/模型规模配置，不给未经验证的固定学习率。优先围绕已用学习率做较小倍率对照，并监控基线保护任务与协议指标，不以训练 loss 下降替代外部任务收益。

数据曝光按 task 和能力分层控制。四个成功轨迹全部保留归档，但训练权重不能隐式等于成功数；可按每个 task 的 k 条合格轨迹分配 1/k 权重，再选择不同合法执行路径。避免相同业务实例因四次都容易成功而主导训练。

工具序列化必须做完整往返检查：原始 tool schema/messages → 目标模型 chat template → 训练 token/labels → 模型原生输出 → 网关解析 → 相同工具调用。检查工具参数名称、数字/布尔类型、嵌套 JSON、tool_call_id 配对、assistant/user/tool 边界、思考结束标记与停止词。先排除空输出、双重解析、调用既留在文本又再次执行等机制问题。

**八、验收顺序与不应采用的补救**

P0：重建只读统计索引，固定评测代码与网关版本；以相同任务、trial seeds、用户模型、temperature/top_p/reasoning_effort/max_steps 比较基线和训练后版本。至少做多 trial 复测，按 task 配对报告区间，并保留基础设施失败的原始尝试记录。正式分数与剔除已确认任务矛盾后的诊断分数分别呈现。

P0：确认实际训练文件和 token 级监督；完成序列化往返测试。明确语义不变的解析修复可以验证，但不能用自动 unlock、自动改写错误枚举/参数、自动追加漏掉的业务写入来掩盖模型缺陷。若测试 agent scaffold，须作为独立实验，并对训练前后模型一视同仁。

P1：建立原生业务后端的最小任务族；20-task 试跑应覆盖核心业务、用户交接、额外写入、错误整条路径及至少六个包含真实依赖的长任务。正例、合法替代路径、针对性负例均需通过验证器测试。任务有效性、教师成功率、训练后迁移收益是三个不同验收层级。

P1：做 300–500-task 的小规模 SFT 消融。放行扩大生成需要同时看到：官方开发集的配对改善、新实例验证改善、基线保护能力没有明显损失、协议/幻觉工具错误没有恶化。不能只以 V2 teacher_pass@4 高或导出数增加为放行条件。

P2：验证通过后冻结新配额、模型设置和预算，再扩大至 3000。必要时再探索偏好学习：同一公开前缀上的正确动作与已确认错误动作构成对比；不把超时、审核未决和框架失败当作语义负例。

建议新增诊断指标：真实工具发现率、必须对象召回率、错误对象写入率、参数类型正确率、政策分支正确率、数值误差、用户实际执行覆盖率、错误升级率、额外写入率、业务状态差异、协议记录差异、首次工具调用格式成功率和基础设施完成率。动作存在、动作执行成功和最终目标完成必须分别统计。

**九、现有数据如何处置**

保留原 8179 行、8105 行 reasoning 版本、所有失败/超时、审核和证据绑定；不覆写。将当前数据定位为经过验证的案例处理/工具交互辅助数据，限制其训练占比，单独做移除它是否改善的消融。对中间错误动作调整监督，对 reasoning 单独审核与版本化。56 个准入缺口和1392个历史不完整槽位继续保留真实状态，补齐数量不能替代重新验证合成方向。
